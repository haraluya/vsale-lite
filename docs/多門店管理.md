## 1. 方案總覽

根據 Vsale-lite 目前的技術架構（Next.js 15 + Supabase + Vercel），以下提供四種多門店部署方案：

| 方案 | 適用情境 | 技術複雜度 | 維護成本 | 資料隔離 |
|------|---------|----------|---------|---------|
| **方案一** | 2-10 個門店 | ⭐ 簡單 | ⭐⭐ 中等 | ✅ 完全隔離 |
| **方案二** | 完全獨立門店 | ⭐⭐ 中等 | ⭐⭐⭐ 高 | ✅ 完全隔離 |
| **方案三** | 10+ 個門店 | ⭐⭐⭐ 複雜 | ⭐ 低 | ⚠️ 邏輯隔離 |
| **方案四** | 商業化 SaaS | ⭐⭐⭐⭐ 非常複雜 | ⭐ 低 | ✅ 可配置 |

## 2. 方案一：共用程式碼庫（推薦）

### 📝 架構說明

```
GitHub (haraluya/vsale-lite)
    └─ main (主程式碼)
        ├─ 門店 A → 自己的 Vercel + Supabase
        ├─ 門店 B → 自己的 Vercel + Supabase
        └─ 門店 C → 自己的 Vercel + Supabase
```

### 🏗️ 實施步驟

#### 門店方操作流程

1. **申請 Supabase 專案**
   ```bash
   # 1. 前往 https://supabase.com/
   # 2. 建立新專案 (選擇區域: ap-southeast-1)
   # 3. 複製以下資訊：
   #    - Project URL
   #    - anon (public) key
   #    - service_role key
   ```

2. **執行 Migration 建立資料庫結構**
   ```bash
   # 在本機安裝 Supabase CLI
   npm install -g supabase

   # 登入 Supabase
   supabase login

   # 連結到門店的 Supabase 專案
   supabase link --project-ref YOUR_PROJECT_REF

   # 執行 Migration（建立所有資料表）
   supabase db push
   ```

3. **申請 Vercel 專案**
   ```bash
   # 1. 前往 https://vercel.com/
   # 2. Import Git Repository
   # 3. 選擇 haraluya/vsale-lite
   # 4. 設定專案名稱（如: vsale-store-a）
   ```

4. **設定 Vercel 環境變數**
   ```env
   # 必要環境變數
   NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_ANON_KEY
   SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_KEY

   # 備份系統（可選）
   CRON_SECRET=隨機生成的金鑰
   GCS_PROJECT_ID=門店的_GCS_專案_ID
   GCS_BUCKET_NAME=門店的_備份_Bucket
   GCS_SERVICE_ACCOUNT_KEY=門店的_服務帳號_JSON

   # 資料庫直連（可選）
   DB_HOST=db.YOUR_PROJECT_REF.supabase.co
   DB_PORT=5432
   DB_NAME=postgres
   DB_USER=postgres
   DB_PASSWORD=YOUR_DB_PASSWORD
   ```

5. **部署專案**
   ```bash
   # Vercel 會自動部署
   # 部署完成後會得到 URL（如: https://vsale-store-a.vercel.app）
   ```

### ✅ 優點

1. **程式碼統一管理**
   - 所有門店共用同一份程式碼
   - 修復 Bug 一次，所有門店受益
   - 新功能開發一次，所有門店可用

2. **資料完全隔離**
   - 每個門店有獨立的 Supabase 專案
   - 資料安全性高，不會互相干擾
   - 符合資料保護法規（GDPR、PDPA）

3. **部署彈性**
   - 門店可選擇是否更新到最新版本
   - 可在 Vercel 設定自動部署或手動部署
   - 可在測試環境驗證後再更新生產環境

4. **成本可控**
   - Supabase 免費方案：500MB 資料庫 + 50,000 月活躍用戶
   - Vercel 免費方案：無限部署 + 100GB 頻寬
   - 適合中小型門店（< 1000 用戶）

5. **易於推廣**
   - 門店僅需申請 Vercel + Supabase（無需技術背景）
   - 提供標準化 SOP 文件
   - 可遠端協助設定

### ❌ 缺點

1. **版本管理複雜**
   - 不同門店可能使用不同版本
   - 需要維護版本相容性（Migration 向後相容）
   - 難以追蹤各門店使用的版本

2. **技術支援成本**
   - 每個門店都需要個別設定
   - 門店遇到問題需要個別排查
   - 需要教育門店管理員基本操作

3. **Migration 管理**
   - 新 Migration 需要每個門店手動執行
   - 可能因門店忘記執行 Migration 導致錯誤
   - 需要建立 Migration 回滾機制

4. **更新推送困難**
   - 無法強制門店更新
   - 需要通知每個門店手動觸發重新部署
   - 可能導致版本碎片化

## 3. 方案二：獨立程式碼庫

### 📝 架構說明

```
GitHub
    ├─ haraluya/vsale-lite (原始專案)
    ├─ store-a/vsale-lite (門店 A Fork)
    │   └─ Vercel + Supabase (門店 A)
    ├─ store-b/vsale-lite (門店 B Fork)
    │   └─ Vercel + Supabase (門店 B)
    └─ store-c/vsale-lite (門店 C Fork)
        └─ Vercel + Supabase (門店 C)
```

### 🏗️ 實施步驟

1. **門店 Fork 原始專案**
   ```bash
   # 1. 前往 https://github.com/haraluya/vsale-lite
   # 2. 點擊右上角「Fork」按鈕
   # 3. 選擇門店的 GitHub 帳號
   # 4. Fork 完成後會得到獨立倉庫（如: store-a/vsale-lite）
   ```

2. **門店客製化修改**
   ```bash
   # 門店可自由修改程式碼
   git clone https://github.com/store-a/vsale-lite.git
   cd vsale-lite

   # 修改品牌 Logo、顏色、文案等
   # 提交變更到自己的倉庫
   git add .
   git commit -m "自訂品牌設定"
   git push origin main
   ```

3. **設定 Vercel + Supabase**（同方案一）

4. **同步上游更新（可選）**
   ```bash
   # 設定上游倉庫
   git remote add upstream https://github.com/haraluya/vsale-lite.git

   # 拉取上游更新
   git fetch upstream

   # 合併更新（可能需要解決衝突）
   git merge upstream/main

   # 推送到門店倉庫
   git push origin main
   ```

### ✅ 優點

1. **完全獨立**
   - 門店擁有完整的程式碼控制權
   - 可自由客製化功能與設計
   - 不受原始專案更新影響

2. **資料與程式碼雙重隔離**
   - 各門店有獨立的 GitHub 倉庫
   - 各門店有獨立的 Supabase 專案
   - 最高等級的隔離性

3. **客製化彈性**
   - 可針對特定門店需求開發功能
   - 可修改 UI/UX 符合品牌形象
   - 可整合門店特有的第三方服務

4. **版本固定**
   - 門店可選擇停留在特定版本
   - 不會被強制更新
   - 適合對穩定性要求極高的門店

### ❌ 缺點

1. **維護成本極高**
   - Bug 修復需要逐一通知每個門店
   - 每個門店需要手動合併更新
   - 可能因合併衝突導致更新失敗

2. **技術門檻高**
   - 門店需要懂 Git 操作（Fork、Merge、Conflict Resolution）
   - 需要有能力解決合併衝突
   - 不適合無技術背景的門店

3. **版本碎片化嚴重**
   - 無法追蹤各門店使用的版本
   - 各門店可能使用完全不同的程式碼
   - 難以提供技術支援（每個門店程式碼都不同）

4. **功能分享困難**
   - 門店 A 開發的功能無法自動同步到門店 B
   - 需要手動 Cherry-pick 特定 Commit
   - 增加重複開發的浪費

5. **安全性風險**
   - 門店可能引入安全漏洞
   - 難以追蹤與修復全域性安全問題
   - 需要每個門店自行維護安全性

#### C. 提供 Migration 監控

```typescript

// - 待合併的更新清單

```

### 💰 成本估算

## 4. 方案三：Multi-Tenant 架構（進階）

### 📝 架構說明

```
GitHub (haraluya/vsale-lite)
    └─ Multi-Tenant 版本
        └─ Vercel (單一部署)
            └─ Supabase (單一資料庫)
                ├─ tenant: store-a
                ├─ tenant: store-b
                └─ tenant: store-c
```

### 🏗️ 核心概念

**單一程式碼 + 單一資料庫 + 多租戶隔離**

#### 資料庫設計

```sql
-- 新增 tenant_id 到所有資料表

-- 1. 新增 tenants 表
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  slug TEXT UNIQUE NOT NULL,           -- 門店代碼（如: store-a）
  name TEXT NOT NULL,                  -- 門店名稱
  domain TEXT UNIQUE,                  -- 自訂網域（可選）
  logo_url TEXT,
  theme_colors JSONB,                  -- 客製化配色
  status TEXT DEFAULT 'active',
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. 修改現有資料表（範例：profiles）
ALTER TABLE profiles ADD COLUMN tenant_id UUID REFERENCES tenants(id);

-- 3. 修改 RLS Policy（範例：profiles）
CREATE POLICY "Profiles: Tenant Isolation"
  ON profiles
  FOR ALL
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

#### 中介軟體設計

```typescript
// middleware.ts
import { createServerClient } from '@supabase/ssr'
import { NextResponse } from 'next/server'

export async function middleware(request: Request) {
  const url = new URL(request.url)
  const hostname = url.hostname

  // 1. 根據網域或子網域識別 Tenant
  // store-a.vsale.app → tenant_slug: store-a
  // vsale.app/store-a → tenant_slug: store-a

  let tenantSlug = ''

  if (hostname.includes('.vsale.app')) {
    // 子網域模式
    tenantSlug = hostname.split('.')[0]
  } else {
    // 路徑模式
    tenantSlug = url.pathname.split('/')[1]
  }

  // 2. 查詢 Tenant 資訊
  const supabase = createServerClient(/* ... */)
  const { data: tenant } = await supabase
    .from('tenants')
    .select('*')
    .eq('slug', tenantSlug)
    .single()

  if (!tenant) {
    return NextResponse.redirect(new URL('/404', request.url))
  }

  // 3. 設定 Supabase 的 Tenant Context
  await supabase.rpc('set_tenant_context', { tenant_id: tenant.id })

  // 4. 傳遞 Tenant 資訊給後續 Server Components
  const response = NextResponse.next()
  response.headers.set('x-tenant-id', tenant.id)
  response.headers.set('x-tenant-slug', tenant.slug)

  return response
}
```

#### Server Actions 修改

```typescript
// lib/actions/products.ts
export async function getProducts() {
  const tenantId = headers().get('x-tenant-id')

  const supabase = await createClient()
  const { data } = await supabase
    .from('products')
    .select('*')
    .eq('tenant_id', tenantId) // 自動過濾 Tenant

  return data
}
```

### ✅ 優點

1. **維護成本極低**
   - 單一程式碼庫，修復 Bug 一次生效
   - 單一部署，更新一次全部門店受益
   - 不需要逐一通知門店更新

2. **功能開發高效**
   - 新功能開發一次，所有門店立即可用
   - 不需要重複開發
   - 可快速迭代

3. **版本管理簡單**
   - 所有門店使用相同版本
   - 不會有版本碎片化問題
   - 易於追蹤與監控

4. **成本效益高（大量門店）**
   - 單一 Vercel 專案可服務所有門店
   - 單一 Supabase 專案（可升級到 Team Plan）
   - 規模化成本降低

5. **跨租戶功能**
   - 可實現跨門店報表
   - 可實現跨門店庫存調撥
   - 可實現集團統一管理

### ❌ 缺點

1. **技術複雜度極高**
   - 需要大幅度重構現有程式碼
   - 需要重新設計資料庫架構
   - 需要實作 Tenant 隔離機制

2. **開發成本高**
   - 預估需要 80-120 小時開發時間
   - 需要完整測試（避免資料洩漏）
   - 需要建立 Tenant 管理介面

3. **資料隔離風險**
   - 若 RLS Policy 設定錯誤，可能導致資料洩漏
   - 需要嚴格的測試與稽核機制
   - 不符合部分資料保護法規（要求物理隔離）

4. **效能瓶頸**
   - 單一資料庫需要處理所有門店流量
   - 可能需要升級 Supabase 方案
   - 需要建立快取機制

5. **客製化困難**
   - 門店無法自由修改程式碼
   - 客製化需求需要透過設定檔實現
   - 可能無法滿足特殊需求

6. **單點故障風險**
   - 若系統故障，影響所有門店
   - 需要建立高可用性架構
   - 需要完善的監控與告警

### 🔧 實施步驟（完整重構）

#### Phase 1: 資料庫重構（2-3 週）

1. **建立 tenants 表與管理介面**
2. **新增 tenant_id 到所有資料表**
3. **重寫所有 RLS Policy**
4. **建立 Migration 腳本**

#### Phase 2: 中介軟體與 Context（1-2 週）

1. **實作 Tenant 識別邏輯（網域/路徑）**
2. **建立 Tenant Context Provider**
3. **修改 Supabase Client 初始化**

#### Phase 3: Server Actions 重構（2-3 週）

1. **修改所有 Server Actions 加入 tenant_id 過濾**
2. **修改所有 Database Queries**
3. **建立 Tenant-aware Helper Functions**

#### Phase 4: UI 客製化系統（1-2 週）

1. **建立 Theme Provider（讀取 tenants.theme_colors）**
2. **建立 Logo 上傳與管理**
3. **建立 Tenant 設定頁面**

#### Phase 5: 測試與部署（2-3 週）

1. **建立完整的測試案例（防止資料洩漏）**
2. **進行安全性稽核**
3. **進行效能測試**
4. **建立監控與告警系統**

### 💰 成本估算

#### 開發成本
- **開發時間**: 80-120 小時
- **測試時間**: 40-60 小時
- **人力成本**: 1 位資深開發者 × 4-6 週

#### 基礎設施成本（支援 100 個門店）
- **Vercel Pro**: $20 USD/月（或 Enterprise）
- **Supabase Team**: $599 USD/月（100GB 資料庫 + 200GB 檔案儲存）
- **CDN**: $50 USD/月（如使用 Cloudflare）
- **監控**: $20 USD/月（如使用 Sentry）

#### 平均成本（100 個門店）

- 比方案一節省 85% 成本（$45.5 → $6.89）

## 5. 方案四：白標 SaaS 模式（長期規劃）

### 📝 架構說明

```
Vsale SaaS Platform
    ├─ 註冊與訂閱系統
    ├─ Multi-Tenant 架構（方案三）
    ├─ 自訂網域管理
    ├─ 計費與發票系統
    └─ 門店自助管理後台
```

### 🏗️ 核心功能

#### A. 門店自助註冊

```
1. 門店訪問 https://vsale.app/register
2. 填寫資料：
   - 門店名稱
   - 門店代碼（slug）
   - 管理員 Email
   - 選擇方案（Free / Pro / Enterprise）
3. 系統自動建立 Tenant
4. 系統發送歡迎郵件（含登入連結）
```

#### B. 訂閱計費系統

| 方案 | 價格 | 功能限制 |
|------|------|---------|
| **Free** | $0/月 | 100 商品 / 500 訂單/月 / 1GB 儲存 |
| **Pro** | $29/月 | 無限商品 / 無限訂單 / 10GB 儲存 |
| **Enterprise** | 客製報價 | 客製功能 / 專屬支援 / 自訂網域 |

#### C. 自訂網域管理

```typescript
// 門店可在後台設定自訂網域
// 1. 門店新增網域: shop.example.com
// 2. 系統顯示 DNS 設定指示:
//    CNAME shop.example.com → vsale.app
// 3. 系統自動申請 SSL 憑證
// 4. 系統自動驗證網域
```

#### D. 門店管理後台

- 門店品牌設定（Logo、配色、favicon）
- 門店資訊管理
- 訂閱方案管理
- 使用量監控（商品數、訂單數、流量）
- 發票下載

### ✅ 優點

1. **商業化潛力**
   - 可收取月費或年費
   - 可提供增值服務
   - 可建立長期穩定收入

2. **用戶體驗極佳**
   - 門店無需任何技術背景
   - 自助註冊，5 分鐘開店
   - 提供完整的教學與支援

3. **維護成本極低**
   - 同方案三（Multi-Tenant）
   - 所有門店使用相同版本
   - 易於維護與更新

4. **規模化能力**
   - 可支援 1000+ 個門店
   - 基礎設施成本隨規模降低
   - 可透過 CDN 優化效能

### ❌ 缺點

1. **開發成本極高**
   - 預估需要 200-300 小時開發時間
   - 需要建立完整的 SaaS 基礎設施
   - 需要建立客服與支援系統

2. **法律與合規**
   - 需要處理 GDPR / PDPA 合規
   - 需要提供隱私政策與服務條款
   - 需要處理資料出境問題

3. **金流與計費**
   - 需要整合 Stripe / PayPal
   - 需要處理發票與稅務
   - 需要處理退款與爭議

4. **客服與支援**
   - 需要建立 FAQ / 文件中心
   - 需要提供 Email / Chat 支援
   - 需要處理門店的各種問題

5. **競爭與市場**
   - 需要與現有 SaaS 競爭（Shopify、91APP）
   - 需要投入行銷資源
   - 需要建立品牌與信任

### 🔧 實施步驟（完整商業化）

#### Phase 1: Multi-Tenant 架構（3-4 個月）

## 7. 建議決策流程

### 決策樹

```
開始
 │
 ├─ 是否打算商業化？
 │   ├─ 是 → 預估門店數量？
 │   │   ├─ < 50 個 → 方案三（Multi-Tenant）
 │   │   └─ > 50 個 → 方案四（白標 SaaS）
 │   └─ 否 → 繼續
 │
 ├─ 門店數量？
 │   ├─ 2-10 個 → 門店是否需要深度客製化？
 │   │   ├─ 是 → 方案二（獨立程式碼庫）
 │   │   └─ 否 → 方案一（共用程式碼庫）✅ 推薦
 │   └─ > 10 個 → 方案三（Multi-Tenant）
 │
 └─ 門店技術能力？
     ├─ 無技術背景 → 方案一（提供 SOP）
     ├─ 基礎技術能力 → 方案一
     └─ 有開發團隊 → 方案二
```

### 情境分析

#### 情境 1：幫助 3 個親友門店使用
**建議**: **方案一（共用程式碼庫）** ✅

**理由**:
- 門店數量少，個別設定可接受
- 門店可能沒有技術背景，提供 SOP 協助設定
- 無需商業化，成本為 0（使用免費方案）
- 可隨時更新，門店選擇是否同步

**實施步驟**:
1. 建立 `docs/STORE_DEPLOYMENT_SOP.md` 文件
2. 協助 3 個門店申請 Vercel + Supabase
3. 協助設定環境變數與部署
4. 建立 LINE 群組提供技術支援

#### 情境 2：推廣給 20-30 個門店
**建議**: **方案三（Multi-Tenant）** ✅

**理由**:
- 門店數量多，逐一設定成本過高
- 統一管理，降低維護成本
- 可提供更好的使用者體驗（自助註冊）
- 基礎設施成本可控（單一 Supabase 專案）

**實施步驟**:
1. 投入 3-4 個月進行 Multi-Tenant 重構
2. 建立門店自助註冊系統
3. 提供免費方案吸引門店加入
4. 建立完整的文件與支援系統

#### 情境 3：門店需要深度客製化（如整合特殊 ERP）
**建議**: **方案二（獨立程式碼庫）** ✅

**理由**:
- 門店有特殊需求，無法透過設定滿足
- 門店有技術團隊，可自行維護
- 門店願意承擔更新成本

**實施步驟**:
1. 協助門店 Fork 專案
2. 提供客製化開發指引
3. 建立 `custom/` 資料夾分層架構
4. 提供上游同步指南

#### 情境 4：計畫商業化，成為批發訂貨 SaaS
**建議**: **方案四（白標 SaaS）** ✅

**理由**:
- 長期商業規劃，值得投資
- 可建立穩定的訂閱收入
- 可服務大量門店（100-1000+）
- 可與現有 SaaS 競爭

**實施步驟**:
1. 投入 6-8 個月進行完整開發
2. 建立商業計畫與定價策略
3. 進行市場調查與競品分析
4. 建立行銷與推廣計畫
