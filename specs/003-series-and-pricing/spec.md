# Feature Specification: 商品系列與等級價格管理

**Feature Branch**: `003-series-and-pricing`
**Created**: 2026-01-02
**Status**: Draft
**Input**: 升級商品管理系統：實作三層階層架構（分類 > 系列 > 產品）與等級價格機制

## 目標

將商品管理系統從「分類 > 產品」雙層架構升級為「分類 > 系列 > 產品」三層架構，並實作核心的等級綁定價格機制，解決目前價格無法根據會員等級差異化的問題。

## User Scenarios & Testing

### User Story 1 - 客戶瀏覽系列並查看等級價格 (Priority: P0)

批發客戶登入系統後，希望能清楚看到自己會員等級對應的優惠價格，並與原價比較，了解折扣力度，快速決定是否下單。

**Why this priority**: 這是系統核心價值主張，等級綁定價格是 B2B 批發系統的基礎功能。沒有此功能，系統無法滿足不同客戶看到不同價格的核心需求。

**Independent Test**: 使用「批發」等級帳號登入，進入「美粒果系列」，驗證看到「原價 $60 您的價格 $50（批發）」；切換「零售」等級帳號，驗證看到「原價 $60 您的價格 $60（零售）」。

**Acceptance Scenarios**:

1. **Given** 批發客戶已登入，**When** 進入「飲料 > 美粒果系列」頁面，**Then** 看到系列圖片、描述與該系列下所有產品，每個產品顯示原價與批發價格
2. **Given** 未設定該客戶等級價格的商品，**When** 該客戶瀏覽商品，**Then** 顯示「價格未設定」並禁用加入購物車按鈕
3. **Given** 客戶瀏覽商品，**When** 查看價格資訊，**Then** 不顯示實際庫存數量，僅顯示庫存狀態（充足/緊張/缺貨）

---

### User Story 2 - 管理員設定商品系列與等級價格 (Priority: P0)

管理員需要將商品按系列組織（如「美粒果系列果汁」），並為每個商品設定原價與各等級對應的價格，讓不同等級客戶看到不同價格。

**Why this priority**: 沒有後台設定功能，前台無法展示價格。這是實現等級價格機制的必要條件。

**Independent Test**: 管理員建立「美粒果系列」，上傳系列圖片，新增「蘋果汁 500ml」商品（系統自動編號為 DRK-0001），設定原價 $60，批發價 $50，零售價 $60，經銷商價 $45。驗證前台不同等級客戶看到對應價格。

**Acceptance Scenarios**:

1. **Given** 管理員已登入後台，**When** 建立新系列「美粒果系列」並選擇分類「飲料」，**Then** 系列成功建立，可上傳系列圖片與描述
2. **Given** 系列已建立，**When** 新增商品「蘋果汁 500ml」並選擇系列，**Then** 商品編號自動產生為「DRK-0001」（分類代碼 + 流水號）
3. **Given** 商品已建立，**When** 進入價格管理頁面，**Then** 看到所有會員等級的價格設定表格，可批量設定各等級價格
4. **Given** 商品原價設定為 $60，**When** 設定批發價 $50，零售價 $60，**Then** 儲存成功，不同等級客戶看到對應價格

---

### User Story 3 - 前台使用者查看個人資訊與登出 (Priority: P0)

客戶登入後，希望在頁面頂部清楚看到自己的身份資訊（手機號碼、會員等級），並能隨時登出系統。

**Why this priority**: 導航列是基礎 UX 功能，客戶需要知道自己的會員等級才能理解看到的價格是否為優惠價。登出功能是安全性基本要求。

**Independent Test**: 客戶登入後，頂部導航列顯示「0912345678 | 會員等級: 批發」與登出按鈕。點擊登出後導回登入頁面。

**Acceptance Scenarios**:

1. **Given** 客戶已登入，**When** 進入任一前台頁面，**Then** 頂部導航列顯示手機號碼、會員等級名稱與登出按鈕
2. **Given** 客戶點擊登出按鈕，**When** 確認登出，**Then** 清除 Session 並導回登入頁面
3. **Given** 客戶未登入，**When** 嘗試直接訪問商品頁面，**Then** 自動導回登入頁面

---

### User Story 4 - 系列上下架管理 (Priority: P1)

管理員需要能將整個系列或單一商品暫時下架（如季節性商品、缺貨商品），前台客戶不應看到已下架的系列或商品。

**Why this priority**: 庫存管理的必要功能，避免客戶看到無法下單的商品。但非立即必要（可先手動刪除商品）。

**Independent Test**: 管理員將「美粒果系列」狀態改為 inactive，驗證前台不顯示該系列（即使其下商品是 active）。管理員將系列改回 active，將「蘋果汁」改為 inactive，驗證系列顯示但該商品不顯示。

**Acceptance Scenarios**:

1. **Given** 系列狀態為 active，**When** 管理員將系列改為 inactive，**Then** 前台不顯示該系列及其下所有商品
2. **Given** 系列狀態為 active，商品狀態為 inactive，**When** 客戶瀏覽系列頁面，**Then** 該商品不顯示
3. **Given** 系列與商品狀態均為 active，**When** 客戶瀏覽，**Then** 正常顯示

---

### User Story 5 - 庫存狀態管理（與庫存數量分離） (Priority: P1)

管理員需要手動設定商品的庫存狀態（充足/緊張/缺貨）顯示給客戶，但實際庫存數量僅供內部參考，客戶無法看到真實數字。

**Why this priority**: 重要的業務邏輯，避免客戶得知真實庫存策略。但可以先用統一狀態（如「充足」）暫時上線。

**Independent Test**: 管理員設定商品實際庫存為 -50（欠貨），但庫存狀態設為「充足」，驗證前台顯示「庫存充足」而非負數。

**Acceptance Scenarios**:

1. **Given** 商品實際庫存為負數（-50），**When** 庫存狀態設為「充足」，**Then** 前台顯示「庫存充足」，不顯示實際數字
2. **Given** 商品實際庫存為 100，**When** 庫存狀態設為「緊張」，**Then** 前台顯示「庫存緊張」
3. **Given** 庫存狀態為「缺貨」，**When** 客戶瀏覽，**Then** 顯示「暫時缺貨」但不禁用加入購物車（支援預購）

---

### User Story 6 - 商品編號自動產生 (Priority: P2)

管理員建立新商品時，系統自動根據商品所屬系列的分類代碼（如 DRK）產生唯一編號（如 DRK-0001），無需手動輸入。

**Why this priority**: 重要的使用者體驗優化，避免人為錯誤與重複編號。但可以先用手動輸入暫時上線。

**Independent Test**: 管理員在「飲料 > 美粒果系列」新增商品「蘋果汁」，商品編號自動產生為 DRK-0001。再新增「橘子汁」，編號自動產生為 DRK-0002。

**Acceptance Scenarios**:

1. **Given** 分類代碼為 DRK，**When** 管理員新增該分類下的第一個商品，**Then** 編號自動產生為 DRK-0001
2. **Given** 該分類下已有 DRK-0001，**When** 新增第二個商品，**Then** 編號自動產生為 DRK-0002
3. **Given** 商品已建立，**When** 編輯商品，**Then** 編號欄位為唯讀，無法修改

---

### Edge Cases

- **商品刪除後編號斷號**: 若 DRK-0001 被刪除，下一個商品編號仍為 DRK-0003（不會回填 0001）
- **並發建立商品**: 兩個管理員同時建立商品時，系統必須確保編號不重複（PostgreSQL Function 鎖定機制）
- **系列遷移**: 若商品從「系列 A」遷移到「系列 B」（不同分類），編號不變（保持原有 DRK-0001）
- **未設定價格的商品**: 客戶瀏覽時顯示「價格未設定」，加入購物車按鈕禁用，但不隱藏商品
- **分類代碼衝突**: 新增分類時，代碼必須唯一（3-10 個大寫字母），重複時顯示錯誤訊息
- **系列刪除保護**: 若系列下仍有商品，禁止刪除系列，提示「請先刪除或遷移該系列下的所有商品」

## Requirements

### Functional Requirements

#### 資料結構

- **FR-001**: 系統必須支援三層階層架構：分類 (Category) > 系列 (Series) > 產品 (Product)
- **FR-002**: 分類必須包含代碼欄位（3-10 個大寫字母，如 DRK），用於商品編號生成
- **FR-003**: 系列必須關聯到分類，可上傳單一主圖，可設定狀態（active/inactive）
- **FR-004**: 商品必須關聯到系列（不直接關聯分類），自動產生商品編號（分類代碼 + 4 位流水號）
- **FR-005**: 商品必須包含原價欄位（retail_price），用於顯示折扣力度
- **FR-006**: 商品必須包含庫存狀態欄位（stock_status: 充足/緊張/缺貨），與實際庫存數量分離

#### 等級價格機制

- **FR-007**: 系統必須提供等級價格表（tier_prices），儲存每個商品 × 每個等級的對應價格
- **FR-008**: 前台商品顯示必須根據當前用戶的會員等級，從 tier_prices 查詢對應價格
- **FR-009**: 若商品未設定該等級價格，前台必須顯示「價格未設定」並禁用加入購物車
- **FR-010**: 前台必須同時顯示原價與用戶等級價格（如「原價 $60 您的價格 $50」）

#### 前台功能

- **FR-011**: 前台必須提供導航列，顯示用戶手機號碼、會員等級名稱與登出按鈕
- **FR-012**: 前台商品列表必須改為顯示系列卡片（不顯示商品），點擊系列進入系列詳情頁
- **FR-013**: 系列詳情頁必須顯示系列資訊（圖片、名稱、描述）與該系列下所有商品列表
- **FR-014**: 商品列表（系列詳情頁內）必須顯示商品名稱、圖片、原價、用戶等級價格、庫存狀態與數量選擇器
- **FR-015**: 前台必須不顯示實際庫存數量，僅顯示庫存狀態標籤

#### 後台功能

- **FR-016**: 後台必須提供系列管理功能（CRUD + 圖片上傳）
- **FR-017**: 後台必須提供價格管理頁面，可批量設定商品的各等級價格
- **FR-018**: 後台商品建立表單必須移除編號輸入欄位，改為選擇系列（編號自動產生）
- **FR-019**: 後台分類管理必須新增代碼欄位（3-10 個大寫字母），用於商品編號生成
- **FR-020**: 後台商品編輯必須新增庫存狀態選擇器（充足/緊張/缺貨）
- **FR-021**: 後台商品編輯必須新增原價輸入欄位（decimal(10,2)，可為空）

#### 商品編號自動產生

- **FR-022**: 商品建立時，系統必須自動產生商品編號，格式為「分類代碼-流水號」（如 DRK-0001）
- **FR-023**: 流水號必須為 4 位數字，每個分類獨立計數
- **FR-024**: 商品編號建立後不可修改（前台、後台均唯讀）
- **FR-025**: 並發建立商品時，系統必須確保編號唯一性（PostgreSQL Function + UNIQUE 約束）

#### 上下架邏輯

- **FR-026**: 系列與商品必須各有獨立的 status 欄位（active/inactive）
- **FR-027**: 前台顯示商品的條件為：系列 active **AND** 商品 active
- **FR-028**: 系列下架（inactive）時，該系列及其下所有商品在前台隱藏
- **FR-029**: 商品下架（inactive）時，僅該商品在前台隱藏，系列仍顯示

#### 安全性與權限

- **FR-030**: 等級價格表（tier_prices）允許所有已認證用戶讀取，Server Action 必須過濾 `tier_id`
- **FR-031**: 前台查詢價格時，Server Action 必須從資料庫 JOIN tier_prices，不信任前端傳遞的價格
- **FR-032**: 訂單建立時（未來功能），必須重新從資料庫查詢價格，不使用前端計算的價格

### Key Entities

#### Series（系列）
- **用途**: 組織商品的中間層，如「美粒果系列果汁」
- **關聯**:
  - 屬於某個分類（category_id），可為 NULL（未分類）
  - 包含多個商品（一對多關係）
- **屬性**: 名稱、描述、圖片 URL、狀態（active/inactive）、排序權重

#### TierPrice（等級價格）
- **用途**: 儲存每個商品在每個會員等級的對應價格
- **關聯**:
  - 屬於某個會員等級（tier_id）
  - 屬於某個商品（product_id）
- **屬性**: 價格（decimal(10, 2)）
- **約束**: (tier_id, product_id) 唯一組合鍵

#### Product（商品 - 更新）
- **新增屬性**:
  - `series_id` (UUID, NOT NULL) - 取代原有的 `category_id`
  - `retail_price` (DECIMAL(10, 2), NULLABLE) - 原價/建議售價
  - `stock_status` (ENUM: sufficient/low/out_of_stock) - 庫存狀態
- **移除屬性**:
  - `category_id` - 商品不再直接關聯分類，改為透過系列關聯

#### Category（分類 - 更新）
- **新增屬性**:
  - `code` (VARCHAR(10), UNIQUE, NOT NULL) - 分類代碼，用於商品編號生成（如 DRK, SNK）

## Success Criteria

### Measurable Outcomes

- **SC-001**: 客戶能在 3 秒內理解自己的會員等級價格與原價的差異（前台顯示清晰）
- **SC-002**: 管理員能在 5 分鐘內完成一個系列的建立與 5 個商品的價格設定
- **SC-003**: 系統支援 10 個管理員同時建立商品，編號不重複（並發安全性）
- **SC-004**: 不同等級客戶瀏覽同一商品，看到的價格必須正確對應其會員等級（100% 準確）
- **SC-005**: 前台客戶無法得知實際庫存數量（隱私保護）
- **SC-006**: 系列下架後，前台即時隱藏該系列（無需手動清除快取）

## Assumptions

1. 假設商品表不包含價格欄位（已在 002-product-management 確立），價格將在本功能實作
2. 假設會員等級表（tiers）已存在，包含等級名稱與排序權重
3. 假設現有商品（若有）可透過資料遷移移至「未分類系列」，不會遺失
4. 假設商品編號格式為「分類代碼-流水號」（如 DRK-0001），不需要其他格式
5. 假設系列與商品的上下架邏輯為「獨立控制，前台聯合判斷」
6. 假設庫存狀態由管理員手動設定，不自動根據庫存數量判斷
7. 假設原價（retail_price）為選填欄位，未設定時僅顯示用戶等級價格
8. 假設系列圖片使用現有的 products Storage bucket，路徑格式為 `series/{series_id}/main.{ext}`
9. 假設前台購物車功能尚未實作，本功能僅實作價格顯示邏輯
10. 假設商品遷移系列後，編號不變（保持原有編號）

## Out of Scope

- 商品多圖上傳（僅支援單一主圖，系列圖片同樣僅單一主圖）
- 商品規格/屬性管理（尺寸、顏色等）
- 商品批量匯入/匯出功能
- 價格歷史記錄追蹤
- 價格自動調整機制（如批量漲價 10%）
- 多層系列結構（如系列 > 子系列 > 商品）
- 商品庫存自動扣減（購物車下單後扣庫存將在未來功能實作）
- 商品標籤/篩選功能（如「熱銷」、「新品」）
- 商品評論/評分功能

## Dependencies

- **001-user-tier-management**: 需要會員等級表（tiers）與用戶資料表（profiles）
- **002-product-management**: 需要商品表（products）與分類表（categories）作為基礎
- Supabase Storage: 需要 `products` bucket 用於儲存系列圖片
- PostgreSQL Function: 需要 `update_updated_at_column()` 函式（已存在）

## Technical Notes

### 資料庫 Migration 策略

1. **Phase 1**: 新增 series 表、tier_prices 表，修改 categories 表（新增 code）
2. **Phase 2**: 為每個分類建立「未分類系列」，將現有商品遷移到對應系列
3. **Phase 3**: 修改 products 表（新增 series_id, retail_price, stock_status，移除 category_id）
4. **Phase 4**: 建立商品編號自動產生邏輯（PostgreSQL Function + Trigger）
5. **Phase 5**: 更新 RLS 策略（series, tier_prices, products）

### 自動編號邏輯

- 使用 PostgreSQL Function `generate_product_code(series_id)` 自動產生編號
- Trigger `trigger_auto_generate_product_code` 在 INSERT 前執行
- 並發安全性由 PostgreSQL 事務鎖定 + UNIQUE 約束保證

### 前台價格查詢邏輯

```typescript
// 偽代碼
getSeriesProductsWithPrice(series_id) {
  1. 取得當前用戶的 tier_id
  2. 查詢 products (JOIN series, 僅 active)
  3. 批量查詢 tier_prices (WHERE tier_id = user.tier_id)
  4. 合併價格資料 (user_price)
  5. 回傳商品列表（含 user_price 與 retail_price）
}
```

### RLS 策略要點

- `tier_prices` 表允許所有已認證用戶讀取（Server Action 負責過濾 tier_id）
- `products` 表的 RLS 改為聯合判斷 `series.status AND products.status`
- `series` 表的 RLS 僅允許客戶讀取 active 系列，管理員可見全部

## Risks

### 高風險

1. **資料遷移導致商品遺失**:
   - **緩解措施**: Migration 前備份資料庫，先在測試環境驗證

2. **商品編號並發重複**:
   - **緩解措施**: PostgreSQL Function 事務鎖定 + UNIQUE 約束 + 測試

3. **前後端價格不一致**:
   - **緩解措施**: 前台、訂單建立均從資料庫查詢價格，不信任前端

### 中風險

4. **RLS 策略權限洩漏**:
   - **緩解措施**: Server Action 明確過濾 tier_id，測試不同等級帳號

5. **系列圖片儲存路徑衝突**:
   - **緩解措施**: 使用 `series/{series_id}/main.{ext}` 格式，與商品圖片區隔
