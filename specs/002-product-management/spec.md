# Feature Specification: 商品管理系統

**Feature Branch**: `002-product-management`
**Created**: 2026-01-02
**Status**: Draft
**Input**: 建立商品管理系統功能，包含後台商品 CRUD、商品分類管理、庫存管理（支援負庫存）、商品圖片上傳、商品基本資料、商品搜尋與篩選功能、前台商品列表展示。不包含價格設定（價格將在下一個功能實作）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理員建立商品基本資料 (Priority: P1)

批發商收到新貨品時，需要快速將商品資訊建立到系統中，包含商品名稱、編號、描述、庫存數量、單位等基本資訊。管理員可以在後台輸入商品資料，系統會驗證商品編號的唯一性，並儲存商品資料。

**Why this priority**: 商品基本資料是整個系統的核心，沒有商品就無法設定價格、無法讓客戶下單。這是商品管理的最基礎功能。

**Independent Test**: 管理員可以建立至少 5 個不同的商品，每個商品都有唯一的編號，可以獨立查看商品詳情，不需要分類或圖片功能即可驗證。

**Acceptance Scenarios**:

1. **Given** 管理員在商品管理頁面，**When** 點擊「新增商品」並輸入商品名稱「冷凍水餃」、編號「P001」、庫存「100」、單位「包」，**Then** 系統成功儲存並在商品列表中顯示該商品
2. **Given** 系統已有商品編號「P001」，**When** 管理員再次使用相同編號建立商品，**Then** 系統顯示錯誤訊息「此商品編號已存在」
3. **Given** 管理員建立商品時輸入負數庫存「-50」，**When** 點擊儲存，**Then** 系統成功儲存（支援負庫存，表示欠貨或預購）
4. **Given** 管理員未輸入必填欄位（商品名稱或編號），**When** 點擊儲存，**Then** 系統顯示錯誤訊息「請填寫所有必填欄位」

---

### User Story 2 - 管理員管理商品分類 (Priority: P1)

批發商需要將商品分類管理，例如「冷凍食品」、「乾貨」、「飲料」等，方便客戶瀏覽和管理員整理。管理員可以建立、編輯、刪除商品分類，並在建立商品時選擇分類。

**Why this priority**: 分類管理是商品組織的基礎，能大幅提升客戶瀏覽效率和管理員管理效率。雖然技術上可以沒有分類，但對批發業務來說，分類是必要的。

**Independent Test**: 管理員可以建立至少 3 個分類，將商品分配到不同分類中，並驗證刪除分類時的保護機制（已有商品的分類無法刪除）。

**Acceptance Scenarios**:

1. **Given** 管理員在分類管理頁面，**When** 點擊「新增分類」並輸入分類名稱「冷凍食品」、排序「1」，**Then** 系統成功儲存並在分類列表中顯示
2. **Given** 管理員建立商品時，**When** 選擇分類「冷凍食品」，**Then** 商品成功關聯到該分類
3. **Given** 某分類已有商品使用，**When** 管理員嘗試刪除該分類，**Then** 系統顯示警告訊息「此分類已有 X 個商品使用，無法刪除」並阻止操作
4. **Given** 某分類尚未有商品使用，**When** 管理員刪除該分類，**Then** 系統成功刪除並從列表中移除

---

### User Story 3 - 管理員編輯商品資訊與庫存 (Priority: P1)

批發商需要經常更新商品資訊（如描述、庫存數量），當進貨或出貨時需要調整庫存。管理員可以在商品列表中點擊編輯，修改商品資料並儲存。

**Why this priority**: 庫存管理是批發業務的日常操作，必須能快速更新庫存數量。商品資訊也會隨時變更（如描述、單位）。

**Independent Test**: 管理員可以編輯已建立的商品，修改名稱、描述、庫存等欄位，驗證庫存可以更新為負數（欠貨情境）。

**Acceptance Scenarios**:

1. **Given** 管理員在商品列表頁面，**When** 點擊某商品的「編輯」按鈕並修改庫存從「100」改為「150」，**Then** 系統更新庫存並在列表中顯示新數值
2. **Given** 管理員編輯商品時將庫存改為「-20」，**When** 點擊儲存，**Then** 系統成功儲存負庫存（表示欠貨 20 個單位）
3. **Given** 管理員編輯商品時，**When** 嘗試修改商品編號欄位，**Then** 系統顯示唯讀狀態或提示「商品編號建立後無法修改」
4. **Given** 管理員編輯商品時更換分類，**When** 點擊儲存，**Then** 系統成功更新商品分類

---

### User Story 4 - 管理員上傳商品圖片 (Priority: P2)

批發商希望在商品頁面顯示商品圖片，方便客戶識別商品。管理員可以在建立或編輯商品時上傳單一主圖，圖片儲存在 Supabase Storage 中。

**Why this priority**: 圖片能提升客戶體驗，但在 MVP 階段，即使沒有圖片也能完成下單流程。因此優先級較低，可以稍後加入。

**Independent Test**: 管理員可以為商品上傳圖片（JPG/PNG/WebP），驗證圖片成功儲存並在商品詳情頁顯示，也可以替換或刪除圖片。

**Acceptance Scenarios**:

1. **Given** 管理員在商品編輯頁面，**When** 點擊「上傳圖片」並選擇一張 JPG 圖片，**Then** 系統成功上傳並顯示圖片預覽
2. **Given** 管理員上傳超過 5MB 的圖片，**When** 點擊上傳，**Then** 系統顯示錯誤訊息「圖片大小不可超過 5MB」
3. **Given** 管理員上傳非圖片格式檔案（如 PDF），**When** 點擊上傳，**Then** 系統顯示錯誤訊息「僅支援 JPG、PNG、WebP 格式」
4. **Given** 商品已有圖片，**When** 管理員上傳新圖片，**Then** 系統替換舊圖片並刪除舊圖片檔案（避免佔用空間）

---

### User Story 5 - 管理員搜尋與篩選商品 (Priority: P2)

批發商的商品數量可能達到數百甚至上千個，管理員需要快速找到特定商品進行編輯或查看。管理員可以使用商品名稱、編號、分類進行搜尋和篩選。

**Why this priority**: 搜尋功能能大幅提升管理效率，但在商品數量較少時（< 50 個），手動翻頁也能接受。因此優先級為 P2。

**Independent Test**: 管理員可以在商品列表頁面輸入關鍵字（如「水餃」），系統即時篩選並顯示符合的商品，也可以使用分類篩選器。

**Acceptance Scenarios**:

1. **Given** 系統已有 100 個商品，**When** 管理員在搜尋框輸入「水餃」，**Then** 系統即時篩選並顯示所有名稱或編號包含「水餃」的商品
2. **Given** 管理員在商品列表頁面，**When** 使用分類篩選器選擇「冷凍食品」，**Then** 系統只顯示該分類的商品
3. **Given** 管理員同時使用搜尋和分類篩選，**When** 輸入「水餃」並選擇「冷凍食品」，**Then** 系統顯示同時符合兩個條件的商品
4. **Given** 管理員搜尋不存在的商品，**When** 輸入「xyz123」，**Then** 系統顯示「查無商品」訊息

---

### User Story 6 - 前台客戶瀏覽商品列表 (Priority: P2)

客戶登入前台後，可以瀏覽商品列表，查看商品名稱、圖片、描述、庫存狀態。客戶可以依分類篩選商品，方便尋找需要的商品。注意：此階段不顯示價格，價格將在下一個功能（003-price-management）實作。

**Why this priority**: 客戶瀏覽商品是下單的前置步驟，但在 MVP 階段，可以先讓管理員完成商品建立和測試，客戶瀏覽功能可以稍後加入。

**Independent Test**: 客戶可以登入前台，瀏覽商品列表，依分類篩選商品，查看商品詳情（不含價格），驗證庫存顯示正確（包含負庫存的顯示方式）。

**Acceptance Scenarios**:

1. **Given** 客戶已登入前台，**When** 進入商品列表頁面，**Then** 系統顯示所有可用商品（名稱、圖片、庫存狀態）
2. **Given** 客戶在商品列表頁面，**When** 選擇分類「冷凍食品」，**Then** 系統只顯示該分類的商品
3. **Given** 客戶查看庫存為正數的商品，**When** 查看商品詳情，**Then** 顯示「庫存：100 包」
4. **Given** 客戶查看庫存為負數的商品（欠貨），**When** 查看商品詳情，**Then** 顯示「欠貨：20 包（可預購）」

---

### Edge Cases *(已決策)*

- **商品編號格式**: ✅ 強制驗證正則表達式 `/^[A-Za-z0-9-_]+$/`，僅允許英數字、連字號、底線，確保 URL 與資料庫安全性
- **商品編號變更**: ✅ 商品編號建立後不可修改（業務主鍵），若需變更應建立新商品並停用舊商品
- **商品名稱重複**: ✅ 允許不同商品使用相同名稱（僅商品編號唯一），例如不同廠牌的「水餃」可用不同編號區分
- **分類刪除**: ✅ 提供「遷移商品至其他分類」功能，允許管理員批量遷移後再刪除分類（見 FR-009-A）
- **商品刪除**: ✅ 訂單使用快照機制（將商品名稱、價格等必要資料複製到 order_items），商品可直接刪除不影響歷史訂單（見延伸功能說明）
- **圖片檔案命名**: ✅ 使用商品 ID 命名，路徑格式 `products/{product_id}/main.{ext}`，符合 plan.md 設計
- **負庫存下單**: ✅ 允許客戶針對負庫存商品下單，無數量限制，完全支援預購業務（符合 Constitution VI）
- **庫存同步**: ⏸️ MVP 階段不處理併發更新問題（Assumption 9），若未來出現問題可引入樂觀鎖機制
- **圖片儲存空間**: ⏸️ MVP 階段使用 Supabase 免費額度（Assumption 3），未來可引入圖片壓縮或 CDN

## Requirements *(mandatory)*

### Functional Requirements

#### 商品基本資料管理

- **FR-001**: 系統必須允許管理員建立商品，包含商品名稱、商品編號、描述、庫存數量、單位
- **FR-002**: 系統必須驗證商品編號的唯一性與格式（正則: `/^[A-Za-z0-9-_]+$/`），不允許重複或非法格式的商品編號
- **FR-003**: 系統必須允許管理員編輯現有商品的所有欄位（除了 id、商品編號 (code)、建立時間）
- **FR-004**: 系統必須允許管理員刪除商品，但需檢查是否已有訂單使用該商品（保護機制）
- **FR-005**: 系統必須支援負庫存數值（表示欠貨或預購狀態）
- **FR-006**: 系統必須在必填欄位（商品名稱、商品編號）未填寫時顯示錯誤訊息

#### 商品分類管理

- **FR-007**: 系統必須允許管理員建立商品分類，包含分類名稱和排序數字
- **FR-008**: 系統必須允許管理員編輯現有分類的名稱和排序
- **FR-009**: 系統必須在刪除分類前檢查是否有商品使用該分類，若有則阻止刪除並顯示警告訊息
- **FR-009-A**: 系統必須提供「分類遷移」功能，允許管理員將某分類的所有商品批量遷移至其他分類後再刪除
- **FR-010**: 系統必須在建立或編輯商品時提供分類選擇器，列出所有可用分類
- **FR-011**: 系統必須根據排序數字由小到大顯示分類列表

#### 商品圖片管理

- **FR-012**: 系統必須允許管理員上傳單一商品主圖（JPG、PNG 或 WebP 格式）
- **FR-013**: 系統必須限制上傳圖片的檔案大小不超過 5MB
- **FR-014**: 系統必須驗證上傳檔案的格式（檔案副檔名與 MIME type），僅接受 JPG、PNG、WebP 格式
- **FR-015**: 系統必須在替換圖片時刪除舊圖片檔案，避免佔用儲存空間
- **FR-016**: 系統必須使用 Supabase Storage 儲存圖片，並產生公開 URL 供前台顯示

#### 商品搜尋與篩選

- **FR-017**: 系統必須支援依商品名稱關鍵字即時搜尋商品
- **FR-018**: 系統必須支援依商品編號關鍵字即時搜尋商品
- **FR-019**: 系統必須支援依商品分類篩選商品列表
- **FR-020**: 系統必須在商品列表提供分頁功能，支援使用者選擇每頁顯示 20、50 或 100 筆

#### 前台商品展示

- **FR-021**: 系統必須在前台商品列表顯示商品名稱、圖片、描述、庫存狀態
- **FR-022**: 系統必須在前台支援依分類篩選商品
- **FR-023**: 系統必須在前台顯示庫存狀態：正數顯示「庫存：X 單位」，負數顯示「欠貨：X 單位（可預購）」
- **FR-024**: 系統**不得**在前台顯示價格（價格將在 003-price-management 功能實作）

#### 資料驗證與安全

- **FR-025**: 系統必須使用 Zod Schema 驗證所有商品資料輸入
- **FR-026**: 系統必須在 Server Actions 中檢查管理員權限（role === 'admin'）
- **FR-027**: 系統必須阻止非管理員角色執行商品建立、編輯、刪除操作，前端與後端皆需驗證
- **FR-028**: 系統必須在訂單建立時將商品資料快照（product_name, deal_price 等）複製到 order_items，確保商品刪除後訂單仍可查詢（延伸功能，004-shopping-cart 實作）

### Key Entities

- **商品 (Product)**: 代表批發商銷售的商品項目。包含屬性：商品名稱、商品編號（唯一）、描述、庫存數量（可為負數）、單位（如：包、箱、瓶）、所屬分類（關聯至 Category）、圖片 URL、建立時間、更新時間。
- **商品分類 (Category)**: 代表商品的分類層級，用於組織商品。包含屬性：分類名稱、排序數字（用於列表排序）、建立時間。

### 資料關聯

- 每個商品可以關聯到一個分類（多對一關係）
- 每個分類可以被多個商品使用（一對多關係）
- 當分類被商品使用時，該分類無法被刪除
- 商品圖片儲存在 Supabase Storage，商品表只儲存圖片 URL

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員可以在 2 分鐘內完成新商品建立流程（從點擊新增到儲存成功）
- **SC-002**: 系統能正確處理 100% 的負庫存案例（不阻擋儲存，正確顯示欠貨狀態）
- **SC-003**: 圖片上傳成功率達 95% 以上（5MB 以內的合法格式圖片）
  - **測量方法**: 執行自動化測試上傳 100 張圖片（包含邊界值測試），記錄成功/失敗次數。驗證腳本位於 `tests/performance/image-upload.spec.ts`
- **SC-004**: 管理員可以在 3 秒內透過商品名稱或編號搜尋找到特定商品（即時搜尋響應）
  - **測量方法**: 使用 Lighthouse CI 或 `tests/performance/search-benchmark.spec.ts` 測量搜尋 API 回應時間（p50, p95, p99），在包含 100+ 商品的資料集中執行
- **SC-005**: 系統能防止 100% 的重複商品編號註冊案例
- **SC-006**: 分類的刪除保護機制生效率達 100%（已使用的分類無法被刪除）
- **SC-007**: 前台客戶可以正確瀏覽商品列表，庫存顯示準確率達 100%（包含負庫存的正確顯示）

### 業務價值

- **提升商品管理效率**: 管理員可以快速建立和更新商品資訊，減少人工錯誤
- **支援預購業務**: 負庫存機制讓批發商可以接受預購訂單，不因暫時缺貨而損失商機
- **改善客戶體驗**: 商品圖片和分類讓客戶更容易找到需要的商品
- **建立價格基礎**: 商品資料是後續「等級綁定價格」功能的先決條件

## Assumptions *(assumptions made during spec creation)*

1. **商品編號格式**: 假設系統允許英數字、連字號、底線作為商品編號（格式: `/^[A-Za-z0-9-_]+$/`），不限制長度，只要求唯一性。商品編號建立後不可修改。
2. **單一主圖限制**: 假設在 MVP 階段，每個商品只需要一張主圖即可滿足需求。若未來需要多張圖片，可在後續版本加入圖片庫功能。
3. **圖片儲存**: 假設使用 Supabase Storage 的免費額度足以支撐 MVP 階段的圖片儲存需求。若圖片數量過多，可引入圖片壓縮或 CDN。
4. **負庫存策略**: 假設批發業務允許負庫存下單（預購或欠貨），系統不阻擋負庫存商品的下單操作。具體下單限制將在 004-shopping-cart 功能中定義。
5. **商品刪除策略**: 假設在 MVP 階段，已有訂單的商品無法刪除（硬刪除保護）。若未來需要刪除，應設計為「軟刪除」以保留訂單紀錄的完整性。
6. **分類階層**: 假設商品分類為單層結構（不支援子分類），符合批發業務的簡單分類需求。若未來需要多層分類，可在後續版本加入。
7. **搜尋效能**: 假設初期商品數量在 500 個以內，使用簡單的模糊搜尋即可滿足效能需求。若商品數量超過 5000 個，可能需要引入全文搜尋或索引優化。
8. **圖片格式**: 假設支援 JPG、PNG 和 WebP 格式（現代瀏覽器主流支援），不支援 GIF、AVIF 等其他格式。若未來需要支援更多格式，可調整驗證邏輯。
9. **併發更新**: 假設在 MVP 階段，管理員同時編輯同一商品的情況較少，不需要實作樂觀鎖或悲觀鎖。若未來出現併發問題，可引入版本號機制。
10. **價格欄位**: 假設商品表**不包含**價格欄位，價格將在 003-price-management 功能中實作（tier_id + product_id 的組合鍵儲存）。

## Out of Scope *(explicitly excluded from this feature)*

- 商品價格設定（將在 003-price-management 功能實作）
- 等級綁定價格機制（將在 003-price-management 功能實作）
- 購物車與下單功能（將在 004-shopping-cart 功能實作）
- **訂單快照機制**（FR-028）：當商品資訊（名稱、單位等）更新後,歷史訂單應保留當時的商品資訊,避免訂單記錄失真。此機制將在 004-shopping-cart 功能中實作,透過在 `order_items` 表中儲存商品快照欄位（`product_snapshot` JSONB）來保存下單當時的商品資料。本功能僅需確保商品資料完整性,不實作快照邏輯。
- 商品多圖上傳（MVP 階段只支援單一主圖）
- 商品規格/屬性管理（如：尺寸、顏色等）
- 商品批量匯入/匯出功能（可在後續版本加入）
- 商品庫存自動扣減（將在訂單功能中實作）
- 商品銷售統計與報表（可在後續版本加入）
- 多層分類結構（MVP 階段只支援單層分類）
- 商品複製功能（可在後續版本加入）
- 商品標籤/標記功能（如：熱銷、新品等）
- 商品 SEO 優化（如：meta description、keywords）
