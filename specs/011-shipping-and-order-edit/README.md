## 功能概覽

### A. 運費設定系統

**目標**: 為不同會員等級設定運費規則，自動化運費計算

**核心功能**:
- ✅ 每個會員等級獨立設定運費（基本運費、滿額免運門檻）
- ✅ 訂單建立時自動計算運費
- ✅ 優惠券折扣不影響免運門檻（依原始商品金額判斷）
- ✅ 管理員可手動調整訂單運費

**使用者故事**:
- **US1**: 管理員設定會員等級運費規則
- **US2**: 客戶結帳時查看運費金額
- **US5**: 優惠券與運費互動邏輯

---

### B. 訂單修改系統

**目標**: 管理員可彈性修改訂單內容，完整記錄修改歷程

**核心功能**:
- ✅ 修改商品單價、數量
- ✅ 加入/移除商品
- ✅ 新增自訂費用項目（手續費、包裝費等）
- ✅ 修改運費（切換免運）
- ✅ 直接修改總金額（減免）
- ✅ 完整修改歷程記錄

**使用者故事**:
- **US3**: 管理員修改訂單
- **US4**: 客戶/管理員查看修改歷程
- **US6**: 訂單狀態流程調整（移除 confirmed）

## 技術亮點

### 資料庫設計

**新增資料表**:
- `order_custom_fees`: 自訂費用項目（手續費、包裝費、總額調整）

**擴展現有資料表**:
- `tiers`: 新增 `shipping_fee`, `free_shipping_threshold`
- `orders`: 新增 `shipping_fee`
- `order_timelines`: 新增 `modifications` JSONB 欄位

**PostgreSQL Functions**:
- `calculate_shipping_fee()`: 運費計算（依用戶等級與商品金額）
- `mark_order_as_shipping()`: 標記出貨並扣減庫存（取代 confirm_order）
- `update_order_with_modifications()`: 批次修改訂單（原子性操作）

### 訂單狀態流程調整

**舊流程**:
```
pending → confirmed (扣庫存) → shipping → completed
```

**新流程**:
```
pending → shipping (扣庫存) → completed
```

**好處**:
- 簡化流程，減少狀態轉換
- 修改訂單時不涉及庫存問題（僅 pending 可修改）
- 出貨與庫存扣減同步

## 使用案例範例

### 案例 1：零售客戶下單（收運費）

**情境**:
- 客戶等級：零售（運費 100 元，滿 1000 免運）
- 商品金額：800 元
- 優惠券折扣：0 元

**計算**:
```
商品合計: NT$800
優惠券折扣: NT$0
運費: NT$100 (未滿 1000)
───────────────────
訂單總額: NT$900
```

---

### 案例 2：零售客戶下單（滿額免運）

**情境**:
- 客戶等級：零售（運費 100 元，滿 1000 免運）
- 商品金額：1200 元
- 優惠券折扣：300 元

**計算**:
```
商品合計: NT$1200
優惠券折扣: -NT$300
運費: NT$0 (原始金額 1200 滿足免運)
───────────────────
訂單總額: NT$900
```

**重點**: 免運門檻依原始商品金額（1200），不看折扣後金額（900）

---

### 案例 3：管理員修改訂單

**情境**:
- 訂單狀態：pending（待確認）
- 客戶反應商品 A 數量過多，想改成 3 個
- 管理員額外收取手續費 60 元

**操作步驟**:
1. 進入訂單詳情頁，點擊「編輯訂單」
2. 修改商品 A 數量：5 → 3
3. 點擊「新增費用」，輸入「手續費」、「60」
4. 確認變更摘要，按下「儲存變更」

**修改歷程記錄**:
```
🔧 系統管理員 修改了訂單          2026-01-06 14:30
┌─────────────────────────────────────────┐
│ • 商品 A: 數量 5 → 3                    │
│ • 新增費用: 手續費 +NT$60               │
│ ─────────────────────────────────────   │
│ 訂單總額: NT$1200 → NT$780              │
└─────────────────────────────────────────┘
```

## 關鍵設計決策

### 1. 運費計算時機

**決策**: 訂單建立時計算並儲存（快照機制）

**理由**:
- 避免後續修改會員等級運費設定影響舊訂單
- 方便管理員手動調整個別訂單運費

---

### 2. 優惠券與運費互動

**決策**: 優惠券折扣不影響免運門檻判定

**理由**:
- 避免客戶濫用優惠券「降低免運門檻」
- 免運門檻應基於「實際購買金額」（商品原價）

**範例**:
- 商品 1200 元 + 優惠券 -300 元 = 900 元
- 免運門檻 1000 元 → **依然免運**（依原始 1200 判斷）

---

### 3. 訂單修改限制

**決策**: 僅 `pending` 狀態可修改

**理由**:
- `shipping` 已扣庫存、可能已出貨 → 不可修改
- `completed` / `cancelled` 已完成 → 不可修改
- 避免複雜的庫存回補邏輯

---

### 4. 移除 confirmed 狀態

**決策**: 將庫存扣減時機與出貨流程合併

**理由**:
- 簡化訂單流程（4 個狀態 → 3 個狀態）
- 修改訂單時不涉及庫存問題（pending 狀態未扣庫存）
- 出貨與庫存扣減同步，避免遺漏

**影響**:
- 需更新所有使用 `confirmed` 的程式碼
- Migration 需轉換現有訂單狀態

## 風險評估

### 高風險項目

| 風險 | 影響 | 緩解措施 |
|------|------|---------|
| 移除 confirmed 狀態的相容性 | 現有訂單狀態轉換可能遺失資料 | Migration 完整測試、先在本地驗證 |
| 訂單修改的原子性 | 修改過程錯誤導致資料不一致 | 使用 Transaction、失敗時 ROLLBACK |
| 庫存扣減時機變更 | 新舊邏輯混淆導致庫存錯誤 | 完整回歸測試、確保所有路徑正確 |

### 中風險項目

| 風險 | 影響 | 緩解措施 |
|------|------|---------|
| 優惠券驗證邏輯複雜化 | 訂單修改後優惠券驗證錯誤 | 撰寫詳細測試案例、覆蓋各種情境 |
| 修改歷程 UI 可讀性 | 修改項目過多時介面混亂 | 設計可摺疊/分頁的歷程顯示 |
