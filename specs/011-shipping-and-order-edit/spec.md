## 一、功能概述

### 1.1 背景與動機

在批發業務中，運費管理是重要的成本控制項目。不同會員等級（零售、批發、經銷商）對運費的需求差異極大：
- **批發/經銷商**：通常免運（大量訂購）
- **零售客戶**：需收取運費，但滿額可免運

此外，訂單處理過程中常見以下情境：
- 商品缺貨需替換其他商品
- 客戶臨時增減數量
- 價格標示錯誤需修正
- 收取額外費用（手續費、運費調整）

現有系統缺乏這兩大功能，導致管理員需要手動處理或重新建立訂單，效率低落且缺乏歷史記錄。

### 1.2 目標

**A. 運費設定系統**
- ✅ 每個會員等級可獨立設定運費規則（收費金額、滿額免運門檻）
- ✅ 訂單建立時自動計算運費
- ✅ 優惠券折扣不影響免運門檻判定（依原始商品金額計算）
- ✅ 支援管理員手動調整個別訂單運費

**B. 訂單修改系統**
- ✅ 支援待確認（pending）與已確認（confirmed）狀態訂單的修改
- ✅ 提供直覺的修改介面（編輯模式 + 一次性提交）
- ✅ 完整記錄修改歷程（整合至訂單操作歷史）
- ✅ 支援多種修改類型：
  - 調整商品單價
  - 增減商品數量
  - 加入/移除商品
  - 新增自訂費用項目（手續費、包裝費等）
  - 修改總金額（直接減免）
  - 切換免運狀態

### 1.3 成功指標

- 管理員可在 30 秒內完成運費設定
- 訂單修改操作可在 2 分鐘內完成（含確認）
- 修改歷程清晰可讀，客戶可理解變更內容
- 零資料遺失（所有修改完整記錄）

### US2: 訂單建立時自動計算運費（客戶 + 系統）

**身份**: 客戶
**需求**: 我在結帳時需要知道運費金額
**目的**: 確認最終付款金額

#### 驗收標準

✅ **AC2.1**: 購物車摘要顯示運費預估（依用戶等級）
✅ **AC2.2**: 結帳頁顯示運費明細：
- 若免運：顯示「運費: 免運」（綠色）
- 若收費：顯示「運費: NT$100」（黑色）
- 若差額免運：顯示「再購 NT$200 即可免運」（提示）

✅ **AC2.3**: 訂單總額計算公式：
```
總金額 = 商品合計 - 優惠券折扣 + 運費
```

✅ **AC2.4**: 優惠券折扣**不影響**免運門檻判定
- 範例：商品合計 1200 元，使用 300 元優惠券 → 折扣後 900 元
- 若滿額免運門檻為 1000 元 → **依然免運**（依原始 1200 計算）

✅ **AC2.5**: 訂單建立後，運費金額儲存於訂單記錄中（快照機制）

#### 計算範例

**情境 1：零售客戶（收運費 100 元，滿 1000 免運）**
```
商品合計: NT$800
優惠券折扣: -NT$0
運費: NT$100 (未滿 1000)
───────────────────
訂單總額: NT$900
```

**情境 2：零售客戶 + 優惠券**
```
商品合計: NT$1200
優惠券折扣: -NT$300
運費: NT$0 (原始金額 1200 滿足免運門檻)
───────────────────
訂單總額: NT$900
```

**情境 3：批發客戶（免運）**
```
商品合計: NT$500
優惠券折扣: -NT$50
運費: NT$0 (等級設定免運)
───────────────────
訂單總額: NT$450
```

### US3: 管理員修改訂單（核心功能）

**身份**: 系統管理員
**需求**: 我需要修改訂單的商品、價格、運費等資訊
**目的**: 彈性處理客戶需求變更或訂單錯誤

#### 驗收標準

✅ **AC3.1**: 在訂單詳情頁，當訂單狀態為 `pending` 或 `confirmed` 時，顯示「編輯訂單」按鈕
✅ **AC3.2**: 點擊「編輯訂單」後進入編輯模式：
- 訂單明細變為可編輯狀態
- 顯示「儲存變更」與「取消編輯」按鈕
- 所有修改暫存於前端，按「儲存變更」後一次性提交

✅ **AC3.3**: 支援以下修改類型：

**A. 修改商品單價**
- 在商品單價處點擊編輯圖示
- 輸入新價格（需大於 0）
- 顯示方式：~~原價 NT$50~~ → **NT$40**（紅色）

**B. 修改商品數量**
- 使用 +/- 按鈕調整數量
- 可輸入數字快速設定
- 顯示方式：數量 ~~5~~ → **3**（紅色）

**C. 移除商品**
- 點擊「移除」按鈕
- 商品以刪除線標記（暫存），儲存後才實際移除

**D. 加入新商品**
- 點擊「加入商品」按鈕
- 搜尋商品名稱或編號
- 選擇商品後輸入數量與單價
- 新增商品以「新增」標籤標記（綠色）

**E. 新增自訂費用項目**
- 點擊「新增費用」按鈕
- 輸入費用名稱（例：手續費、包裝費、額外運費）
- 輸入金額（可為負數表示減免）
- 顯示於訂單明細下方，樣式區分於商品項目

**F. 修改運費**
- 在運費欄位點擊編輯
- 輸入新運費金額（可為 0 表示免運）
- 顯示方式：運費 ~~NT$100~~ → **NT$0**（免運，綠色）

**G. 直接修改總金額**
- 在總金額處點擊「調整總金額」
- 輸入最終總金額
- 系統自動計算差額並新增「總額調整」項目
- 範例：原總額 1000，修改為 800 → 新增「總額調整: -NT$200」

✅ **AC3.4**: 修改過程中即時更新總金額預覽
✅ **AC3.5**: 按下「儲存變更」後：
- 跳出確認視窗，顯示所有變更摘要
- 確認後提交至後端
- 成功後重新載入訂單詳情（顯示最新狀態）

✅ **AC3.6**: 若訂單狀態為 `shipping`, `completed`, `cancelled`，則不顯示「編輯訂單」按鈕

### US5: 優惠券與運費互動

**身份**: 系統
**需求**: 優惠券驗證與運費計算需明確分離
**目的**: 避免優惠券濫用，確保運費計算正確

#### 驗收標準

✅ **AC5.1**: 優惠券的 `min_order_amount` 驗證**不包含**運費
✅ **AC5.2**: 免運門檻判定**不包含**優惠券折扣（依商品原始金額）
✅ **AC5.3**: 訂單修改後，若優惠券不符合條件：
- 跳出警告：「訂單修改後不符合優惠券條件（SAVE100 需滿 1000 元），是否移除優惠券？」
- 提供選項：[保留優惠券] [移除優惠券]
- 若選擇保留，顯示警告標記但允許儲存

✅ **AC5.4**: 運費在訂單修改後可單獨調整，不受優惠券影響

#### 計算邏輯範例

**範例 1：優惠券最低金額驗證**
```
商品合計: NT$800
運費: NT$100
優惠券條件: 滿 1000 元可用

驗證邏輯: 800 < 1000 → 優惠券不可用 ❌
（運費不計入最低金額）
```

**範例 2：免運門檻判定**
```
商品合計: NT$1200
優惠券折扣: -NT$500 (SALE500)
折扣後金額: NT$700
免運門檻: 1000 元

免運判定: 1200 >= 1000 → 符合免運 ✅
（依原始商品金額，不看折扣後金額）
```

### US6: 訂單狀態流程調整

**身份**: 系統
**需求**: 移除 `confirmed` 狀態，簡化訂單流程
**目的**: 將庫存扣減時機與出貨流程結合，避免修改訂單時的庫存問題

#### 驗收標準

✅ **AC6.1**: 新的訂單狀態流程：
```
pending (待確認) → shipping (出貨中) → completed (已完成)
       ↓                   ↓
   cancelled          cancelled
```

✅ **AC6.2**: 庫存扣減時機：
- **舊邏輯**：確認訂單（confirmed）時扣減
- **新邏輯**：標記出貨（shipping）時扣減

✅ **AC6.3**: 可修改訂單的狀態：
- `pending`: ✅ 可修改
- `shipping`: ❌ 不可修改（已扣庫存、已出貨）
- `completed`: ❌ 不可修改
- `cancelled`: ❌ 不可修改

✅ **AC6.4**: 取消訂單邏輯：
- `pending` 取消：不涉及庫存回補
- `shipping` 取消：回補庫存（已扣減的部分）
- `completed` / `cancelled`: 不可取消

✅ **AC6.5**: 所有使用 `confirmed` 狀態的程式碼需移除或重構：
- PostgreSQL Functions
- Server Actions
- UI 元件
- 型別定義
- 驗證 Schema

## 三、非功能需求

### 3.1 效能要求

- 訂單修改儲存響應時間 < 1s
- 運費計算響應時間 < 200ms
- 修改歷程查詢響應時間 < 300ms

### 3.2 安全性要求

- ✅ 僅管理員（`role = 'admin'`）可修改訂單
- ✅ 所有修改記錄操作者資訊（`actor_id`, `actor_role`）
- ✅ 客戶可查看修改歷程，但不可修改或刪除
- ✅ RLS Policy 嚴格控制存取權限

### 3.3 相容性要求

- ✅ 現有訂單資料向下相容（Migration 需處理舊資料）
- ✅ 移除 `confirmed` 狀態後，現有訂單需轉換狀態
- ✅ 運費欄位預設為 0（舊訂單未設定運費）

### 3.4 可用性要求

- ✅ 修改介面支援鍵盤操作（Tab、Enter 快速輸入）
- ✅ 修改歷程可摺疊/展開（避免資訊過載）
- ✅ 錯誤訊息清晰易懂（例：「運費不可為負數」）

## 四、技術架構

### 4.1 資料表設計

詳見 [`data-model.md`](./data-model.md)

### 4.2 Server Actions

**運費相關**
- `calculateShippingFee(userId, subtotal)`: 計算運費
- `updateShippingFee(orderId, newFee)`: 修改訂單運費

**訂單修改相關**
- `updateOrderDetails(orderId, modifications)`: 批次修改訂單
- `addOrderItem(orderId, productId, quantity, price)`: 加入商品
- `removeOrderItem(orderItemId)`: 移除商品
- `addCustomFee(orderId, name, amount)`: 新增自訂費用
- `adjustTotalAmount(orderId, finalAmount)`: 直接修改總金額

**狀態流程相關**
- `markAsShipping(orderId)`: 標記出貨（取代 confirmOrder）
- `updateOrderStatus(orderId, newStatus)`: 更新狀態
- `cancelOrder(orderId, reason)`: 取消訂單

### 4.3 PostgreSQL Functions

- `calculate_shipping_fee(user_id, subtotal)`: 運費計算函數
- `mark_order_as_shipping(order_id)`: 標記出貨並扣減庫存（原子性）
- `update_order_with_modifications(order_id, modifications_json)`: 批次修改訂單

### 4.4 Migration 策略

**Phase 1**: 新增運費功能
- 新增 `tiers.shipping_fee`, `tiers.free_shipping_threshold` 欄位
- 新增 `orders.shipping_fee` 欄位
- 新增 `order_custom_fees` 表（自訂費用項目）

**Phase 2**: 移除 confirmed 狀態
- 修改 `orders.status` CHECK 約束
- 更新現有訂單狀態（`confirmed` → `shipping`）
- 重構 PostgreSQL Functions

**Phase 3**: 新增修改歷程記錄
- 擴展 `order_timelines.action_type` 支援 `order_modified`
- 新增 `order_timelines.modifications` 欄位（JSONB）

## 七、風險與挑戰

### 7.1 高風險項目

1. **移除 confirmed 狀態的相容性**
   - 風險：現有訂單狀態轉換可能遺失資料
   - 緩解：Migration 需完整測試，先在本地環境驗證

2. **訂單修改的原子性**
   - 風險：修改過程中系統錯誤導致資料不一致
   - 緩解：使用 PostgreSQL Transaction，修改失敗時 ROLLBACK

3. **庫存扣減時機變更**
   - 風險：新舊邏輯混淆導致庫存錯誤
   - 緩解：完整回歸測試，確保所有路徑正確

### 7.2 中風險項目

4. **優惠券驗證邏輯複雜化**
   - 風險：訂單修改後優惠券驗證邏輯錯誤
   - 緩解：撰寫詳細測試案例，覆蓋各種情境

5. **修改歷程 UI 可讀性**
   - 風險：修改項目過多時介面混亂
   - 緩解：設計可摺疊/分頁的歷程顯示
