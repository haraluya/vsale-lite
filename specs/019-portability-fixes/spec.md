## Feature Overview

### Purpose

將 Vsale-lite 從單一環境硬編碼系統轉變為完全可移植的開源專案，確保任何開發者都能在 2 小時內從複製到部署完成，使用自己的 Vercel + Supabase 環境。

### Background

當前專案存在多個阻礙可移植性的問題：
- 硬編碼的 Supabase 專案 ID 散布在多個檔案中
- 缺少環境變數範本檔案
- 部署文檔特定於現有環境
- 缺少自動化初始化工具
- 潛在的敏感信息洩露風險

這些問題導致新用戶無法順利部署專案到自己的環境。

### Business Value

- **降低進入門檻**：新用戶可在 2 小時內完成部署（當前幾乎不可能）
- **提升專案採用率**：移除技術障礙，吸引更多開發者使用
- **增強安全性**：消除硬編碼憑證，建立安全的配置管理機制
- **改善維護性**：統一環境變數管理，降低維護成本

### Target Users

- **主要用戶**：想要部署 Vsale-lite 到自己環境的新開發者
- **次要用戶**：現有維護者（受益於更清晰的配置管理）

## User Scenarios & Testing

### Scenario 1: 新用戶首次部署

**作為** 一位新開發者
**我想要** 將 Vsale-lite 部署到我的 Vercel 和 Supabase 帳號
**以便** 開始使用這個批發訂貨系統

**步驟**:
1. 從 GitHub Fork 專案
2. 建立新的 Supabase 專案
3. 複製 `.env.local.example` 為 `.env.local`
4. 填入 Supabase URL 和 API 金鑰
5. 執行環境檢查指令驗證配置
6. 執行資料庫 Migration
7. 執行初始化指令建立管理員帳號
8. 在 Vercel 匯入專案並設定環境變數
9. 驗證部署成功

**預期結果**:
- 所有步驟順利完成，無需修改程式碼
- 總時間 < 2 小時
- 系統正常運作，可登入後台

**測試方法**:
- 邀請未接觸過專案的開發者按文檔執行
- 記錄完成時間與遇到的問題
- 成功率目標：90%

---

### Scenario 2: 開發者驗證環境配置

**作為** 開發者
**我想要** 快速驗證環境變數是否正確設定
**以便** 避免因配置錯誤導致應用啟動失敗

**步驟**:
1. 編輯 `.env.local` 檔案
2. 執行 `pnpm check-env` 指令
3. 查看驗證結果

**預期結果**:
- 顯示所有必要環境變數的設定狀態
- 明確指出缺少或格式錯誤的變數
- 提供修正建議

**測試方法**:
- 故意遺漏必要變數，驗證是否正確提示
- 輸入錯誤格式的 URL，驗證格式檢查

---

### Scenario 3: 部署後驗證

**作為** 開發者
**我想要** 驗證線上環境是否正確配置
**以便** 確認部署成功且功能正常

**步驟**:
1. 完成 Vercel 部署
2. 執行 `pnpm verify-deploy https://my-site.vercel.app`
3. 查看驗證報告

**預期結果**:
- 自動測試前台/後台頁面載入
- 驗證環境變數正確性
- 檢查資料庫連線狀態
- 提供通過/失敗報告與除錯建議

**測試方法**:
- 對正確配置的環境執行，應全部通過
- 故意設定錯誤的環境變數，驗證是否偵測到

## Functional Requirements

### FR1: 環境變數範本系統

**優先級**: P0 (阻斷性)

**需求**:
- 系統必須提供 `.env.local.example` 範本檔案
- 範本必須包含所有必要環境變數的說明
- 每個變數必須附帶取得方式的詳細註解
- 範本必須區分必填與可選變數

**驗收標準**:
- [ ] `.env.local.example` 檔案存在於專案根目錄
- [ ] 包含所有 3 個必要變數（SUPABASE_URL, ANON_KEY, SERVICE_ROLE_KEY）
- [ ] 包含所有 8 個可選變數（DB 直連、GCS、站點二）
- [ ] 每個變數都有取得方式的註解
- [ ] 註解使用繁體中文
- [ ] 格式正確，可直接複製使用

---

### FR2: 移除硬編碼專案識別符

**優先級**: P0 (阻斷性)

**需求**:
- 系統不得在程式碼中硬編碼 Supabase 專案 ID
- 所有專案識別邏輯必須動態從環境變數提取
- `vercel.json` 不得包含硬編碼的環境變數值

**驗收標準**:
- [ ] `vercel.json` 移除 `env` 區塊
- [ ] `app/api/env-test/route.ts` 改為動態提取專案 ID
- [ ] `app/api/check-connection/route.ts` 移除硬編碼檢查
- [ ] `restore-backup.js` 使用動態專案 ID
- [ ] `import-data.ps1` 改為從環境變數讀取密碼
- [ ] 執行 `git grep "qwovavytryvgchcowjof"` 僅在文檔中出現（不在程式碼中）

## Key Entities

### 環境變數配置

**屬性**:
- `name`: 變數名稱（如 `NEXT_PUBLIC_SUPABASE_URL`）
- `value`: 變數值
- `required`: 是否必填（boolean）
- `description`: 變數用途說明
- `source`: 取得方式說明
- `validation_pattern`: 驗證格式（如 URL 格式）

**關係**:
- 環境變數範本 (`env.local.example`)
- 環境檢查腳本 (`check-environment.js`)
- 部署文檔

---

### 驗證測試案例

**屬性**:
- `name`: 測試案例名稱
- `path`: API 路徑
- `expected_status`: 預期 HTTP 狀態碼
- `validation_function`: 額外驗證邏輯

**關係**:
- 部署驗證腳本 (`verify-deployment.js`)

## Assumptions & Constraints

### 假設

1. **開發者技能**：目標用戶具備基本的 Git、Node.js、命令列操作知識
2. **前置需求**：用戶已擁有 GitHub、Vercel、Supabase 帳號
3. **網路環境**：用戶可正常訪問 GitHub、Vercel、Supabase 服務
4. **Node.js 版本**：用戶使用 Node.js v22.x 或更高版本
5. **作業系統**：用戶使用 Windows、macOS 或 Linux（PowerShell 腳本需調整）

### 約束

1. **向後相容性**：所有修改不得破壞現有部署環境的功能
2. **資料庫結構**：不修改任何資料表結構或 Migration 檔案
3. **功能範圍**：僅處理可移植性問題，不新增或修改業務功能
4. **語言**：所有文檔、註解、輸出訊息使用繁體中文
5. **工具依賴**：僅使用專案現有的工具鏈（pnpm、Next.js、Supabase CLI）

### 技術約束

1. **環境變數命名**：保持現有命名規範（`NEXT_PUBLIC_` 前綴）
2. **檔案位置**：腳本放置於 `scripts/` 目錄，文檔放置於 `docs/` 目錄
3. **編碼格式**：所有檔案使用 UTF-8 編碼
4. **換行符號**：統一使用 LF（Unix 格式）

## Out of Scope

以下項目明確排除在此功能範圍外：

### 不包含的功能

1. **多雲平台支援**：僅支援 Vercel 部署（不包含 AWS、GCP、Azure）
2. **Docker 容器化**：不提供 Docker 部署方案
3. **CI/CD 工具多樣化**：僅支援 GitHub Actions（不包含 GitLab CI、Jenkins）
4. **自動化備份遷移**：不處理現有資料的自動遷移
5. **圖形化配置介面**：僅提供命令列工具（無 GUI）

### 不修改的內容

1. **資料庫結構**：不修改任何 Migration 或資料表定義
2. **業務邏輯**：不修改任何前後台功能
3. **UI/UX 設計**：不修改任何介面或使用者體驗
4. **測試覆蓋率**：不新增或修改現有測試案例
5. **效能優化**：不處理任何效能相關的改進

### 文檔範圍限制

1. **進階配置**：不包含進階的 Supabase 或 Vercel 配置說明
2. **自訂網域**：不包含自訂網域設定指南
3. **SSL 憑證**：不包含 SSL 憑證配置說明
4. **監控告警**：不包含生產環境監控設定
